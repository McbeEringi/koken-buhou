22 McbeEringi

動機

ブラウザで何かしらのデータを生成した場合、これをユーザーに保存させる手段として<a download>を用いたダウンロードが一般的である。 しかしこの方法を用いる場合、一度に保存できるファイルは一つに限られる。 これを解決する手段として、ZIPやtarなどの複数ファイルを一つのファイルにまとめる機能を持つファイル形式がよく用いられる。 ブラウザ上でこの動作を実現するライブラリは複数存在するが、動作速度やライブラリサイズ等において満足いくものを見つけられなかった。

目標

  • 複数ファイルの一括ダウンロード
    • 📦 汎用 シンプル
    • 🪶 軽量 ( 数kB以内 )
    • ⚡ 爆速 ( 「見逃しちゃうね」 )

ファイルフォーマットの選定

「複数ファイルを一つにまとめたファイル」はアーカイブファイルと呼ばれる。 「元のファイルと同じ内容を表すより容量の小さいファイル」は圧縮ファイルと呼ばれる。 これらは全く独立した概念である。

  • アーカイブのみ
    • tar

      tape_archive tarball 紙テープに穴開けてた時代から使われている

  • 圧縮のみ
    • gzip

      .tar.gzでわりとよくみる

    • bzip2

      .tar.bz2でたまにみる

    • xz

      .tar.xz 逢えたらラッキー

  • アーカイブ及び圧縮
    • 7z

      圧縮解凍ソフト「7-Zip」といえばこれ 高圧縮率

    • LHA

      純日本産

    • ZIP

      いつもの 元は圧縮解凍ソフト「PKZIP」の形式
      様々な端末がデフォルトで対応している

今回の目標はアーカイブファイルの作成に言い換えることができる。 以下の二つの形式を検討した。

  • tar
    • メリット
      • 広く普及している
      • アーカイブ機能のみであるため読み込みもできそう
    • デメリット
      • 歴史が長いので方言が存在
      • スマホで開きづらい
      • ダウンロードボタン押してtarがきたらなんだこれはになる
  • ZIP
    • メリット
      • 広く普及している
      • 正しくファイルが入手できたという安心感がある
      • iOSですら標準ソフトで開ける
    • デメリット
      • 圧縮されている場合は読み込みが辛そう

結果今回はZIP形式を用いることにした。 当然の帰結。

各部詳細

ローカルファイルヘッダとセントラルディレクトリレコードは、ほとんどが共通の内容である。 ディレクトリは、解凍時のZIPファイルの位置を基準とした相対パスをファイル名として記述することで表現される。 全てのマルチバイトな数値は、リトルエンディアンで格納される。 今回はアーカイブのみできればよいので、圧縮方法に非圧縮を指定している。 以下Wikipediaから一部改変して引用する。

MS-DOS date/time format

MS-DOS date/time formatは、ローカルファイルヘッダとセントラルディレクトリレコードにおいて日時の表現に用いられる形式である。 この名前で調べればMicrosoftのリファレンスが出てくる。 タイムゾーンの概念がないことと解像度が2秒であることが特徴である。

YYYYYY=年-1980 MMMM=月 DDDDD=日 hhhhh=時 mmmmmm=分 sssss=秒/2

とするとMS-DOS date/time formatは

MSB <-- --> LSB
YYYYYYYM MMMDDDDD hhhhhmmm mmmsssss

で表される。

CRC-32

CRC-32は、データ破損の検出に用いられる32bitのデータである。 解凍ソフトは、ZIPファイルから得られたデータとヘッダに記録されているCRC-32を比較して、データが破損していないことを確認する。 ZIPファイルを生成する場合はたとえ非圧縮であってもCRC-32を計算してファイルに含める必要がある。

JSで実装

JSでのファイルの扱い

JSでバイナリを扱う際はArrayBufferが用いられる。 これは指定された長さのメモリを表すオブジェクトである。 ArrayBufferを操作するにはTypedArray又はDataViewを用いる。

TypedArrayは、Uint8ArrayやFloat32Arrayなどの総称であり、 ArrayBufferを指定したビット数の要素を持つ配列として扱うことができる。 多バイト型の場合一般的にバイトオーダーはリトルエンディアンであるものとして扱われる。 TypedArrayの主な作成方法は二通りある。 一つは普通のArrayから変換する方法でこの場合ArrayBufferは自動的に作成される。 もう一つはあらかじめ用意したArrayBufferを参照する方法である。

DataViewは多様な数値型を端末のエンディアンに関係なく操作するインターフェースである。 これを用いるとArrayBufferをメソッドを使って操作できる。 こちらはメソッド内でバイトオーダーを指定できるがTypedArrayと比べてパフォーマンスが劣る。 DataViewの作成方法はあらかじめ用意したArrayBufferを参照する方法のみである。

JSではBlobと呼ばれる単位でファイルのような不変の生データを持つオブジェクトを処理する。 これはArrayBufferやTypedArray、DataView、Blob、文字列の集合から作成可能である。 今回はBlobを含む配列を受け取りUint8Arrayの集合としてZIPを生成、Blobを返す関数を実装する。

CRC-32

複数のBlobをただ繋げるだけであればBlobコンストラクタにBlobの配列を入れるだけで良い。 しかしCRC-32の計算には生のバイナリ列が必要なため、一度BlobをUint8Arrayに変換する。

const blob2Ui8A=async blob=>new Uint8Array(await new Response(blob).arrayBuffer());

ResponseのarrayBufferメソッドは非同期である。 BlobにもarrayBufferメソッドは存在するが、iOS14以降の対応なので一度Responseで包んだ。 Blobの内容をUint8Arrayとして得られたらこれを用いてCRC-32を計算する。

gzipについて記述されているRFCの末尾にCRC-32の計算のC言語での実装が載っている。 これをJSに移植した。

// 注意: ビット演算は符号付き32bit整数として扱われる

const
crc_table=[...Array(256)].map((_,n)=>[...Array(8)].reduce(c=>(c&1)?0xedb88320^(c>>>1):c>>>1,n)),
crc=(buf,crc=0)=>~buf.reduce((c,x)=>crc_table[(c^x)&0xff]^(c>>>8),~crc);

さらに簡潔にすると

const
crc=(t=>
  (buf,crc=0)=>~buf.reduce((c,x)=>t[(c^x)&0xff]^(c>>>8),~crc)
)(
  [...Array(256)].map((_,n)=>[...Array(8)].reduce(c=>(c&1)?0xedb88320^(c>>>1):c>>>1,n))
);

crc(await blob2Ui8A(blob));

これでCRC-32が得られた。

MS-DOS date/time format

MSB <-- --> LSB
YYYYYYYM MMMDDDDD hhhhhmmm mmmsssss

の通りに実装する。

const dosDT=d=>(
  ((d.getFullYear()-1980)<<25)|
  ((d.getMonth()+1)<<21)| // 注意: new Date().getMonth()は0~11
  (d.getDate()<<16)|
  (d.getHours()<<11)|
  (d.getMinutes()<<5)|
  (d.getSeconds()>>1)
);

dosDT(new Date());

非同期reduce

カレントディレクトリレコードに記録する「ZIP開始位置に対するローカルファイルヘッダの相対オフセット」の計算には、それ以前のローカルファイルエントリのサイズの合計値が必要である。 これは動的計画法そのものであり、Arrayのreduceメソッドを用いて実装可能である。 しかし各要素に対して非同期処理を含むため少し工夫する必要がある。 以下の例を実行して挙動を確認してもらいたい。

await[...Array(8)].reduce(async(a,_,i)=>(
  console.log('pre',i), // 順番に即時実行
  console.log('core',
    await new Promise(f=>(setTimeout(_=>f(i),3000*Math.random())))// 処理に時間のかかる非同期処理を並列実行
  ),
  a=await a,
  a.push(i),
  console.log('post',i,a), // 完了した非同期処理を含む前の要素の結果を用いて、順番に実行
  a
),[]);

pre ${i}が順番に表示された後、ランダムな順でcore ${i}が表示されながら、post ${i} ${a}が順番に表示されたと思う。 非同期処理の並列実行とその前後の処理を一つのreduceで実現している。

完成品

今回作成したコードはPetitZipの名称でhttps://github.com/McbeEringi/petit/blob/main/zip.mjsにて公開している。

const
zip=(
  w=[],// {name,buffer:ArrayBuffer}、Blob及びFile等の配列
  f=_=>_// 進捗表示用の関数
)=>((
  u=x=>new Uint8Array(x),
  zz=u([0,0]),vz=u([10,0]),pk12=u([80,75,1,2]),pk34=u([80,75,3,4]),// 定数 malloc削減
  le2=x=>u([x,x>>>8]),le4=x=>u([x,x>>>8,x>>>16,x>>>24]),// リトルエンディアン
  cnt=x=>le4(x.reduce((a,y)=>a+(y.byteLength||y.size||0),0)),// データサイズの計算
  te=new TextEncoder(),i=0,
  ddt=x=>// mmmsssss hhhhhmmm MMMDDDDD YYYYYYYM // Y-=1980;s/=2;
    ((x.getFullYear()-1980)<<25)|((x.getMonth()+1)<<21)|(x.getDate()<<16)|
    (x.getHours()<<11)|(x.getMinutes()<<5)|(x.getSeconds()>>1),
  crc=(// https://www.rfc-editor.org/rfc/rfc1952
    t=>(buf,crc=0)=>~buf.reduce((c,x)=>t[(c^x)&0xff]^(c>>>8),~crc)
  )(
    [...Array(256)].map((_,n)=>[...Array(8)].reduce(c=>(c&1)?0xedb88320^(c>>>1):c>>>1,n))
  )
)=>w.reduce(async(a,x,b,n)=>(
  b=x.buffer||x,
  n=te.encode(x.name),
  x=[
    vz,zz,zz,le4(ddt(new Date(x.lastModified))),le4(crc(u(b instanceof ArrayBuffer?b:await new Response(b).arrayBuffer()))),
    x=le4(b.byteLength||b.size),x,le2(n.byteLength),zz
  ],
  f(++i/w.length/2),// 進捗表示
  a=await a,
  f(++i/w.length/2),// 進捗表示
  a.cd.push(pk12,vz,...x,zz,zz,zz,zz,zz,cnt(a.lf),n),// PK0102 vMade x cmtLength 0304disk intAttr extAttrLSB extAttrMSB 0304pos name
  a.lf.push(pk34,...x,n,b),//  PK0304 x name content
  a
),{
  lf:[],// ローカルファイルエントリを格納する配列
  cd:[]// セントラルディレクトリレコードを格納する配列
}).then((x,_=le2(w.length))=>new Blob(
  [...x.lf,...x.cd,u([80,75,5,6]),zz,zz,_,_,cnt(x.cd),cnt(x.lf),zz],// PK0506 disk 0304startDisk cnt0102disk cnt0102all 0102size 0102pos cmtLength
  {type:'application/zip'}
)))();

JSZipと比較

作成したコードの評価のため、広く使われているZIP生成ライブラリであるJSZipと比較する。

サイズ

機能が大きく異なるので単純比較はできないが、 Minify済みのコードにおいてJSZipの902.2kBに対して、PetitZipは1.72kB、 zip関数のみであれば1000Bを切る。

HTMLで複数ファイルの読み込み

複数ファイルをJSで読み込みたい場合は<input type="file" webkitdirectory>を使う。 標準仕様として存在しているが名前にwebkitがついている。

"zip"という言葉

ZIPの制作者がzipという名前を自由に使って良いと表明したらしい。

deflateとzlibとgzipとZIPの関係

  • deflate
    可逆圧縮アルゴリズム
    • ZIP deflateを用いた圧縮が可能なアーカイブファイル形式
    • zlib
      deflateを実装したライブラリ兼ヘッダー/フッターの定義
      • PNG
        可逆圧縮可能な画像形式
        データの圧縮にzlib形式を使用
    • gzip
      deflateを用いた圧縮ファイル形式兼ヘッダー/フッターの定義

圧縮アルゴリズムの特許問題

幾つかの圧縮法は特許を取っている企業が存在した。 GIF画像が使えなくなった騒ぎもこれである。 zlibでの実装は特許に抵触しないように注意深く実装されたらしい。 現在これらの特許は有効期限切れで気にする必要はない。

自己解凍形式について

セントラルディレクトリ終端レコードに記録される「セントラルディレクトリのオフセット」と「ZIPファイルのコメントの長さ」を利用すると、 ZIPファイルの始端と終端に任意のデータを付加することができる。 ここに解凍ソフトを入れて拡張子をexeにしたものが所謂自己解凍exeである。 つまりファイルの始端又は終端に任意のデータを付加可能な形式であれば、理論上どんな形式でも自己解凍プログラムを作成可能である。

ちなみに今回の延長で自己解凍HTML(非圧縮)を作ってみたが、場合によってZIP部が文書に表示されてしまっていまいちだった。
