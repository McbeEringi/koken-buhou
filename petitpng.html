動機

第三者の要望を受けてフォントファイルをビットマップに変換するアプリglyph_gen(https://mcbeeringi.github.io/apps/mc/glyph.html)をWorkerスレッドとOffscreenCanvasを用いてリファクタリングした。 流れでゲームMinecraft用の計算アプリslime_chunk_be(https://mcbeeringi.github.io/apps/mc/slime_.html)を作り直すことにした。 slime_chunk_beはその用途の性質上glyph_genと比較して高速に画像を生成する必要がある。 古いブラウザの場合OffscreenCanvasに対応していないものがある。 しかしWorkerスレッドでOffscreenCanvasが使えない場合に同様の処理をメインスレッドで実行してしまうと、描画をブロックしてしまいブラウザが操作を受け付けない状態になる。 簡易な画像をWorkerスレッド上で高速に描画してメインスレッドでデコードしやすい状態で転送できる仕組みを作る必要が出てきた。

要件

座標を与えるとそれがスライムチャンクであるか否かをBooleanで返す関数slimeがある。 slimeは内部で簡易的なメルセンヌツイスタを実装しており、比較的重い処理である。 半透明の灰色を背景にslime(p)==trueの座標を緑色で示した32*32ピクセルの画像を得たい。 形状の認識をしやすくするため薄く市松模様をかける。 これらは全てWorkerスレッドの中で行われる。

目標

  • 📱 iOS12のWorkerスレッドで動く
  • 💫 ArrayBuffer不使用
  • 🔄️ 同期処理
  • ⚡ 爆速 (標準APIもびっくり!)

手法

既存

計算結果をRGBAに変換したデータを転送して全ての描画をメインスレッドで行う手法である。

  • Workerスレッドでslime計算、色を決定してRGBAの順で配列に格納
  • Uint8ClampedArrayに変換しメインスレッドに転送
  • ImageDataに変換
  • canvasを用意してputImageDataで描画
  • URL.createObjectURL(await canvas.toBlob())でURLを取得
  • img要素にデコード
  • 画面に表示されるcanvasに描画

この手法には多数のデメリットが存在する。

  • TypedArrayは通常の配列に比べてパフォーマンスが劣る
  • canvasを毎度新規で用意する行為はパフォーマンスを大きく低下させる要因
  • 数色しか使用しないにもかかわらずRGBAの状態で転送する行為は情報密度が低く好ましくない

今回

計算結果を可能な限り画像に近づけた状態で転送して最低限の描画をメインスレッドで行う手法である。

  • 画像のバイナリを構成する定数やパレットをあらかじめ用意
  • Workerスレッドでslime計算、色を決定してインデックス番号として配列に格納
  • Base64エンコードしてDataURLを成形、メインスレッドに転送
  • img要素にデコード
  • 画面に表示されるcanvasに描画

既存の手法との比較は以下の通り。

  • メインスレッドでデコードのcanvasを用いない
  • canvasからのURL取得と異なり画像圧縮を挟まないので高速
  • 色をインデックス番号で管理可能なため高効率

画像圧縮を省くことで高速に処理をしたいので、非圧縮の画像フォーマットについて調べた。

    • テキスト形式とバイナリ形式がある

  • BMP

PNG

非圧縮PNG

PNGは可逆圧縮を用いた画像ファイルフォーマットであり、今日において最も普及している画像フォーマットの一つである。 今回は非圧縮のフォーマットに焦点を当てているにもかかわらずなぜPNGが登場するのか。 それはPNGの仕様上圧縮をせずともPNG画像を作成することが可能であるからである。

PNGはそのデータの圧縮にzlibという形式を用いている。 zlibはdeflate圧縮アルゴリズムを実装したライブラリであり、同時にヘッダやフッタの定義も含んでいる。 deflateは広く用いられているデータ圧縮アルゴリズムである。 zipファイルやgzipといった広く用いられる技術の裏側で活躍している。

deflateはデータをある一定サイズ以下のチャンクの並びとして保持する。 チャンクには3種類あり、それぞれダイナミックハフマンブロック、固定ハフマンブロック、非圧縮ブロックである。 このうち非圧縮ブロックを用いることで、deflate、zlib、PNGの仕様を満たした状態で非圧縮のPNG画像が生成可能なのである。

構造

  • 基本的にビッグエンディアン
  • ファイル構造

ファイルヘッダ

8byteの固定のデータである。 PNGファイルであることの確認とファイルの破損の検出のためのもの。

89 50 4e 47 0d 0a 1a 0a

チャンク

ファイルヘッダ以外のすべてのデータはチャンクの中に存在する チャンクは数種類あるが構造は共通である。

  • length ( 4 byte )
    • dataの長さをビッグエンディアンで
  • chunk type ( 4 byte )
    • IHDR, IDATなどのチャンク名
  • data ( n byte )
    • 任意のデータ
  • CRC32 ( 4 byte )
    • データの破損を検出するためのデータ
    • chunk type + dataのCRC32をビッグエンディアンで
    • zipファイルの生成に全く同じものを使ったのでこれを流用した(ZIP編を参照)

代表的なチャンクを以下に挙げる。 幾つかは設置が必須のチャンク( * )であり必ず含める必要がある。

IHDR *

設置が必須のチャンクである。 画像の基本的な情報を格納する。

  • Width ( 4 bytes )
    • 画像の幅
  • Height ( 4 bytes )
    • 画像の高さ
  • Bit depth ( 1 byte )
    • 1ピクセルを表すのに用いるビット数を表す
  • Color type ( 1 byte )
    • 色の扱い方
  • Compression method ( 1 byte )
    • 常に0
  • Filter method ( 1 byte )
    • 常に0
  • Interlace method ( 1 byte )
    • インターレス(Adam7)を使用する(1)か否(0)か

Color typeとBit depthは使用できる値とその組み合わせが決まっている。

Color type Bit depth 機能 説明
0 1,2,4,8,16 グレースケール ピクセルの明るさを{Bit depth}bitで表現
2 8,16 TrueColor ピクセルの色(RGB)を{Bit depth}*3byteで表現
3 1,2,4,8 インデックス パレット(PLTEチャンク)で定義した色を参照
4 8,16 アルファ付き グレースケール ピクセルの明るさと透明度(GA)を{Bit depth}*2bitで表現
6 8,16 アルファ付き TrueColor ピクセルの色と透明度(RGBA)を{Bit depth}*4byteで表現 
00 00 00 0d 49 48 44 52 0 0 0 20 0 0 0 20 2 3 0 0 0 0e 14 92 67
length----- chunk_type- width--- height-- - - - - - CRC32------
13          I  H  D  R  32       32       2bit indexed

PLTE

インデックスモードで用いる色をRGBで列挙する。 順番がそのままインデックス番号になる。

00 00 00 03 50 4c 54 45 ff 00 ff 34 e0 e6 ba
length----- chunk_type- data---- CRC32------
3           P  L  T  E  #ff00ff
{0:#ff00ff}なパレットの定義

tRNS

透明度を指定したい場合に使用する。 グレースケールモードとTrueColorモードにおいてはここで指定した色が透明になる。 インデックスモードにおいては透明度を列挙することで各インデックス番号における透明度を指定できる。 透明度をIDATに書けるモードにおいては使用できない。

00 00 00 01 74 52 4e 53 80 ad 5e 5b 46
length----- chunk_type- da CRC32------
1           t  R  N  S  
インデックス番号0の色の透明度を0x80に設定

IDAT *

設置が必須のチャンクである。 zlibで圧縮した画像データを持つチャンクである。 一つのファイルに複数個のIDATチャンクを含めることができる。 画像データについては後ほど解説する。

00 00 00 06 49 44 41 54 00 01 23 00 45 67 e1 c9 7f 1b
length----- chunk_type- data------------- CRC32------
6           I  D  A  T

IEND *

設置が必須のチャンクである。 ファイルの終端であることを示すチャンク。 これ以降のデータは読み込まれない。 データは常に空でありどのファイルでも以下の通りである。

00 00 00 00 49 45 4e 44 ae 42 60 82
length----- chunk_type- CRC32------
0           I  E  N  D

zlib

zlibはdeflate圧縮アルゴリズムを用いたライブラリ + ヘッダとフッタの定義である。 吐かれるデータはヘッダ+deflateのブロックたち+フッタである。

ヘッダ

  • CMF ( 1 byte )
    • CMF=(CINFO&15)<<4|(CM&15)
    • CINFO ( 4 bits )
      • 圧縮情報
      • deflateで使った窓のサイズを0~7であらわす
    • CM ( 4 bits )
      • 圧縮方式
      • 8がdeflateを表す
  • FLG ( 1 byte )
    • FLG=(FLEVEL&3)<<6|(FDICT&1)<<5|(FCHECK&31)
    • FLEVEL ( 2 bits )
      • 圧縮に使ったアルゴリズムについて
      • 圧縮速度が速 0~3 遅
      • 圧縮結果が大 0~3 小
    • FDICT ( 1 bit )
      • プリセット辞書を使う(1)か否(0)か
    • FCHECK ( 5 bits )
      • データ破損チェック用
      • (CMF<<8|FLG)%31==0になるような数を入れる
  • DICTID ( 4 bytes )
    • FDICT==1の場合に出現

今回は非圧縮ブロックを使うのでヘッダは08 1dになる

deflate

圧縮したデータはPNGのチャンクと同じようにブロックという単位に区切られる。 ブロックには数種類あり生のデータをそのまま入れられる非圧縮ブロックが存在する。

非圧縮ブロック
  • flag ( 1 byte )
    • flag=(BTYPE&3)<<1|(BFINAL&1)
    • BTYPE ( 2 bits )
      • 非圧縮ブロックは0
    • BFINAL ( 1bit )
      • このブロックが最後のブロックの場合に1
  • len ( 2 bytes )
    • dataの長さをリトルエンディアンで
  • nlen ( 2 bytes )
    • lenのビット反転
  • data ( n bytes )
    • ここにデータが入る

以下は01 02 03を2つの非圧縮ブロックに分けて入れる例である。

00 01 00 fe ff 01
01 02 00 fd ff 02 03
  len-- nlen- data-

adler32 (フッタ)

役割も長さもCRC32と同じである。 圧縮前のデータから計算した結果をビッグエンディアンで格納する。 wikipediaを参考に実装した。

adler=data=>{
    let a=1,b=0,len=data.length,tlen,i=0;
    while(len>0){
        len-=(tlen=Math.min(1024,len));
        do{b+=(a+=data[i++]);}while(--tlen);
        a%=65521;b%=65521;
    }
    return(b<<16)|a;
}

PNG画像データ

deflateにかける前のデータである。 圧縮効率を高めるため行毎にフィルターを定義できる。

https://www.w3.org/TR/PNG-Filters.html

0が何もしていない生のデータを表す。 フィルターの種類を表す数は行の先頭に付加する。 データはIHDRで定義した通りに書く。 例えば1pxあたり8bitでインデックス番号が

0123
4567

の画像のデータはフィルター0を使用すると

0 0 1 2 3 0 4 5 6 7
- ------- - -------

になる。

実装

以下が要件を満たす非圧縮PNGを返すJSの実装である。 https://github.com/McbeEringi/mcbeeringi.github.io/blob/b4d608a17eb04bc752fe3801ed2aaf2b89fdf3b2/apps/mc/slime_.html

    137,80,78,71,13,10,26,10,// header

検証

canvasとOffscreenCanvasと今回のPNG生成をメインスレッドで1000回実行して比較した。 単純な画像エンコーダとしての性能を見るため、32*32のノイズを用いた。 OffscreenCanvasにはtoDataURLが存在しないのでtoBlobで代用した。

octx=new OffscreenCanvas(32,32).getContext('2d'),

plte=[[0,255,255,255],[255,0,255,255],[255,255,0,255],[0,0,0,255]],
draw=()=>new Promise(f=>Object.assign(new Image(),{
    onload(){f(this);},
    src:((
        // CRC32
        crct=[...Array(256)].map((_,n)=>[...Array(8)].reduce(c=>(c&1)?0xedb88320^(c>>>1):c>>>1,n)),

        chunk=x=>[...be4(x.length-4),...x,...be4(crc(x))],// データ -> チャンク

        ...chunk(arr('50 4c 54 45  00 ff ff  ff 00 ff  ff ff 00  00 00 00')),// PLTE CMYK

結論

今回のPNG生成手法はcanvasに対して約5倍、OffscreenCanvasに対して約1.5倍高速である問結果が得られた。 目標は十分に達成された。

  • ✅ iOS12のWorkerスレッドで動く
  • ✅ ArrayBuffer不使用
  • ✅ 同期処理
  • ✅ 爆速 (ぶっちぎり)

また、deflateにおいて圧縮は必須ではないこと、OffscreenCanvasはcanvasとは全くの別物であることなどの知見が得られた。 時間があればAPNGの生成にも挑戦したい。
